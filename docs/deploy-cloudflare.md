# Deploying CollegeStat to Cloudflare Workers

Production runs the built vinext Worker (`dist/server`) with static assets (`dist/client`). Production must use the hosted catalogue (`NEXT_PUBLIC_CATALOGUE_SOURCE=supabase`): profiles, search and explore come from Supabase.

## How the bundle stays small

The Worker bundle holds code only. Large read-only datasets are written to `dist/client/data/` by `scripts/build-asset-data.ts` (last step of `npm run build`) and read at request time through the `ASSETS` binding (`server/asset-data.ts`, cached per isolate). The list of datasets is `lib/asset-datasets.ts`. `data/generated/ranking-profiles.json` and `directory-ranking-rows.json` come from `scripts/build-ranking-data.ts` (part of `npm run catalogue`).

Not published (too large, only used by non-hosted mode): `list.json` (50 MB), the 64 catalogue profile shards, `global-directory.json`. In production the hosted-search fallback for publisher-subject queries such as "computer science germany" returns an empty result (see `supabase/proposals/20261114_explorer_tuition_sort_countries.sql`).

Local dev (port 5173) is unchanged: it reads the same files from `data/`.

## Environment

Public values are baked into the build (`define` in `vite.config.ts`). Set them in the shell or an ignored `.env.production.local` before `npm run deploy`; changing one needs a rebuild.

| Name | Kind | Notes |
| --- | --- | --- |
| `NEXT_PUBLIC_SUPABASE_URL` or `VITE_SUPABASE_URL` | public, build | Supabase project URL |
| `NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY` (or `NEXT_PUBLIC_SUPABASE_ANON_KEY` / `VITE_SUPABASE_ANON_KEY`) | public, build | publishable key |
| `NEXT_PUBLIC_CATALOGUE_SOURCE` | public, build | must be `supabase` |
| `NEXT_PUBLIC_SITE_URL` (or `SITE_URL`) | public, build | canonical origin, e.g. `https://collegestat.xyz`; also read by the sitemap step, which defaults to `https://collegestat.xyz` |
| `NEXT_PUBLIC_SUPPORT_URL`, `NEXT_PUBLIC_AUTH_EMAIL_ENABLED`, `NEXT_PUBLIC_AUTH_GOOGLE_ENABLED`, `NEXT_PUBLIC_AUTH_APPLE_ENABLED`, `NEXT_PUBLIC_AUTH_TELEGRAM_ENABLED`, `NEXT_PUBLIC_MAP_STYLE_URL` | public, build | optional |
| `SUPABASE_URL` | runtime var | optional override of the URL on the server |
| `SUPABASE_SECRET_KEY` or `SUPABASE_SERVICE_ROLE_KEY` | secret | staff/admin, account deletion, provider attestation |
| `DEEPSEEK_API_KEY` | secret | tried first for AI answers |
| `GROQ_API_KEYS` (or `GROQ_API_KEY`) | secret | fallback |
| `OPENROUTER_API_KEY` | secret | fallback |
| `OPENAI_API_KEY` | secret | optional |
| `DEEPSEEK_MODEL`, `GROQ_MODEL`, `OPENROUTER_MODEL`, `OPENAI_MODEL`, `OPENROUTER_CONNECTION_READY` | plain var | optional; set under `vars` or with `wrangler secret put` |

Set secrets (the owner runs these; each prompts for the value):

```
node node_modules/wrangler/bin/wrangler.js secret put SUPABASE_SERVICE_ROLE_KEY --name collegestat
node node_modules/wrangler/bin/wrangler.js secret put DEEPSEEK_API_KEY --name collegestat
node node_modules/wrangler/bin/wrangler.js secret put GROQ_API_KEYS --name collegestat
node node_modules/wrangler/bin/wrangler.js secret put OPENROUTER_API_KEY --name collegestat
```

`secret put` needs the Worker to exist: run the first deploy, then set secrets. `dist/server/wrangler.json` is regenerated by each build, so keep non-secret runtime vars out of it; use secrets or the dashboard.

## Deploy

```
export NEXT_PUBLIC_SITE_URL=https://<your-domain>     # before building
npm run deploy      # build, then wrangler deploy --config dist/server/wrangler.json
```

Check first without uploading:

```
npm run build
node node_modules/wrangler/bin/wrangler.js deploy --dry-run --config dist/server/wrangler.json --outdir /tmp/cf-out
```

Preview the built Worker locally: `npm start -- --port 8799` (never 5173).

## Speed: placement, edge cache and warming

- Smart Placement is on (`placement: { mode: "smart" }` in `vite.config.ts`, so it lands in `dist/server/wrangler.json`). Supabase is in Sydney; Cloudflare may run the Worker near it so a cold render's database round trips are short. Static assets are still served from the visitor's edge. The Workers Cache API used by the edge cache is per location, so with placement active, cache hits are served from where the Worker runs: compare `X-Edge-Cache: HIT` timings from Central Asia before and after, and remove the line if hits got slower.
- Public pages (home, `/universities`, `/university/*`, `/rankings`, `/scholarships*`, `/articles*`, `/compare`, info pages) are edge-cached for a day and then served stale for a week while they refresh (`server/edge-cache.ts`). The key includes the build stamp, so every deploy starts a fresh cache. Dashboard, auth, account and other API routes are never cached.
- After each deploy, warm the cache:

```
npm run warm                                   # https://collegestat.xyz
npm run warm -- https://collegestat.xyz --concurrency=8 --langs=en,ru,uz --top=300
```

It requests hub pages in every language and scholarship, target-university (`data/segment/targets.json`) and top-ranked university pages in `--langs`, then re-requests any page that was rendered from the bundled fallback. Only HTML is warmed: client-navigation (RSC) entries are keyed on the page the visitor came from and cannot be warmed generically. The cache is per data center, so a warm run from one place helps that location (or the Smart Placement location) only.

## After the first deploy

1. Note the `https://collegestat.<account>.workers.dev` URL.
2. Supabase, Authentication, URL Configuration: add `https://collegestat.<account>.workers.dev/auth/callback` (and `/auth/reset-password` if you restrict paths) to Redirect URLs; set Site URL to the public origin.
3. Custom domain later: Cloudflare dashboard, Workers & Pages, the Worker, Settings, Domains & Routes, Add custom domain (the zone must be on Cloudflare). Or add `"routes": [{"pattern": "example.com", "custom_domain": true}]` through a wrangler config you keep outside `dist/`. Then set `NEXT_PUBLIC_SITE_URL` to the new origin, rebuild and redeploy (canonical URLs, sitemap and robots.txt use it), and add the new `/auth/callback` to Supabase.
4. Dev-only routes `/zz-preview`, `/zz-preview-db`, `/zz-l3` return 404 in production builds.

## Limits (checked against Cloudflare docs)

Workers limits page: Worker size 64 MiB uncompressed on both plans (no compressed limit listed); CPU 10 ms per request on Free, 30 s default on Paid; 128 MB memory per isolate; Free 50 subrequests, Paid 10,000; static assets 25 MiB per file, 20,000 files Free / 100,000 Paid. `dist/client` has about 9,100 files.

The Free plan's 10 ms CPU limit is the real risk: server-rendered pages cost tens of ms locally, so use the Paid plan.
